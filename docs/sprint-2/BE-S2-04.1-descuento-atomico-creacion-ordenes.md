# BE-S2-04.1 — Descuento atómico en la creación de órdenes

**Estado:** implementado y validado con PostgreSQL aislado. No se ejecutaron migraciones ni seeders en desarrollo o producción y no se hicieron commits ni push.

## 1. Diagnóstico del contrato anterior

El contrato autoritativo sigue siendo `PUT /api/v1/laboratory-orders/{laboratoryOrder}/discount`. Su body es un objeto JSON cerrado con exactamente estos campos:

```json
{"type": "percentage", "value": "10.00"}
```

`type` admite únicamente `percentage` o `amount`. `value` admite un entero JSON o un string decimal positivo con una o dos posiciones decimales; no admite un número JSON fraccionario, cero, negativos, notación exponencial ni más de dos decimales. El servidor normaliza la intención a un string con dos decimales.

Para `percentage`, el valor máximo es `100.00`. Para `amount`, el máximo persistible es `9999999999.99`, correspondiente a `NUMERIC(12,2)`. El cálculo usa centavos enteros: el porcentaje redondea a centavo por mitad hacia arriba y el monto efectivo se limita al subtotal sin modificar la intención persistida. Impuestos continúan en `0.00` bajo el contrato vigente.

El endpoint anterior conserva la restricción de órdenes `pending`, su autorización `orders.manage_discount`, la respuesta `LaboratoryOrderResource`, el evento `order.discount_set` y la eliminación mediante `DELETE /discount` con `order.discount_removed`.

## 2. Contrato de creación ampliado

`POST /api/v1/laboratory-orders` admite ahora la propiedad opcional `discount`, con exactamente el mismo objeto y validador del `PUT`. No acepta campos calculados como `subtotal`, `discount`, `taxes`, `total`, moneda o precios.

```json
{
  "branch_id": 1,
  "patient_id": 42,
  "doctor_id": null,
  "commercial_client_id": null,
  "price_list_id": 3,
  "ordered_at": "2026-10-15 14:30:00",
  "notes": null,
  "exams": [
    {"laboratory_exam_id": 7},
    {"laboratory_exam_id": 9}
  ],
  "discount": {"type": "percentage", "value": 10}
}
```

El ejemplo normaliza `discount.value` a `"10.00"`. Omitir `discount` conserva el comportamiento anterior. `null`, un arreglo, un escalar, un objeto incompleto o claves desconocidas producen 422 con rutas anidadas como `discount.type`, `discount.value` o `discount.subtotal`.

Una orden sin exámenes y sin descuento continúa válida. Una orden sin exámenes con descuento también continúa la semántica ya disponible mediante el `PUT`: conserva `discount_type` y `discount_value`, pero su subtotal, descuento efectivo y total son `0.00`. Un monto superior al subtotal conserva el monto solicitado y limita únicamente el descuento efectivo. Un valor cero es inválido para ambos tipos.

## 3. Permisos

La ruta mantiene `orders.create`. Antes de cualquier escritura, el Request y la action aplican adicionalmente:

- `orders.add_exam` cuando `exams` contiene al menos una selección.
- `orders.manage_discount` cuando la propiedad `discount` está presente, incluso si está mal formada o contiene `null`.

No se crean permisos ni se modifican roles. Un usuario con `orders.create` puede seguir creando una cabecera sin descuento. Incluir descuento sin `orders.manage_discount`, o incluir líneas sin `orders.add_exam`, responde 403 sin cabeceras, líneas, requisitos o auditorías parciales.

## 4. Atomicidad y economía

`CreateLaboratoryOrder` mantiene una transacción exterior única. Dentro de ella crea y audita la cabecera, compone las líneas mediante `AddExamToLaboratoryOrder` y finalmente invoca `SetLaboratoryOrderDiscount`. Esta action conserva su bloqueo de la orden, validación `pending`, cálculo mediante `RecalculateLaboratoryOrderEconomics`/`LaboratoryOrderEconomicCalculator` y auditoría `order.discount_set`.

Las transacciones Laravel anidadas usan la misma conexión y no confirman independientemente de la exterior. Por ello, un fallo de referencia, precio, publicación clínica, requisito, cálculo o auditoría revierte cabecera, líneas, requisitos, intención de descuento, totales y todos los eventos producidos por la solicitud.

El descuento se calcula después de incorporar todas las líneas. Los cambios posteriores de composición continúan recalculando con los precios snapshot y la intención persistida. La creación conserva el orden de bloqueos de BE-S2-04: referencias de cabecera, lista, exámenes ordenados por ID, orden y precios. La aplicación final vuelve a bloquear la orden recién creada dentro de la misma transacción; ninguna otra transacción puede observarla parcialmente.

## 6. Errores y compatibilidad

- 403: falta alguno de los permisos combinados requeridos.
- 422: estructura o valor de descuento inválido, referencias comerciales inválidas o fallo comercial de una línea.
- 409: conserva los conflictos clínicos de composición.
- Un fallo en cualquier examen impide llegar al descuento y revierte toda la creación.
- Un fallo al guardar, recalcular o auditar el descuento revierte también la composición anterior.
- `PUT /discount` y `DELETE /discount` no cambian de contrato.
- No se modifican estados clínicos, versiones, requisitos, muestras, resultados, informes, migraciones ni datos históricos.

## 9. Riesgos y decisiones pendientes

No queda una decisión funcional nueva para descuentos: la orden vacía, el límite por subtotal y la precisión proceden del contrato anterior. El frontend debe tratar `value` como intención decimal exacta y no enviar importes calculados. Los consumidores que validan claves exactas del request deben admitir la nueva propiedad opcional; la respuesta no agrega claves nuevas.
